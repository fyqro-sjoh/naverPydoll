# 다중 프로필 수집 서비스 설계 (수집 엔진과 외부 API)

작성일: 2026-11-26, 고침: 2026-11-27. 상태: 설계(미구현).
2026-11-26 판은 독립 감사를 거쳤다 (9장). 2026-11-27 에 고친 부분(2장의 새 사실, 3.1, 3.4, 4장, 6장, 8장)은
아직 감사를 받지 않았다.

2026-11-27 에 사용자가 확정한 결정 21개를 반영했다. 결정의 원문과 근거는 `docs/decisions/engine-design.md` 에 있고,
이 문서에서는 해당 위치에 (Q번호)로 표시한다.

**용어**: 이 문서의 "인스턴스"는 프로필 1개 + 출구(프록시) 1개 + 브라우저 신원 1개 + 워커 1개의 묶음이다.
서비스는 이 묶음을 여러 개 동시에 돌린다. 묶음의 짝은 한 번 정하면 바꾸지 않는다.

## 1. 목표

1. 통과된 프로필 여러 개를 동시에 운영해 수집한다. 고정 프록시 수만큼 인스턴스를 띄운다 (프록시 1개 = 프로필 1개 = 인스턴스 1개).
2. 외부에서 HTTP API로 검색을 요청하면 **원본(source)** 과 **정리된 JSON** 을 돌려준다.

## 2. 지금까지 확인된 사실 (계획의 전제)

| 사실 | 근거 | 계획에 미치는 영향 |
| --- | --- | --- |
| 통과한 프로필을 재사용하면 보안 확인 없이 열린다 | 직접 연결에서 시험함. IP가 바뀌어도 통과 상태가 유지되는지는 모름 | 인스턴스마다 프로필을 유지하고, 프로필과 IP의 짝을 바꾸지 않는다 |
| 같은 프로필로 Chrome을 동시에 두 개 띄울 수 없다 | 시험함 | 인스턴스 하나는 한 번에 작업 하나만 처리한다 |
| 출구 IP가 요청마다 바뀌는 프록시에서 필터 요청이 차단됐다 | 시험함. 원인이 IP 변경이라는 것은 추정 | 프록시는 IP가 고정되는 것만 쓴다 (0단계에서 검증) |
| 보안 확인은 Slack으로 사람에게 전달해 통과할 수 있다 | 1회 시험함. 오답 재시도, 늦은 답, 동시 발생은 미확인 | 인스턴스 등록과 재발 대응에 쓴다 |
| Linux 신원은 바로 차단된다. Linux 컨테이너에서 Windows 신원을 써도 로그인 페이지로 넘겨져 목록을 받지 못한다 | 시험함 (조건별 1~2회, `windows_identity_test.md`) | 엔진은 macOS 또는 Windows 기기에서 돌린다. Docker 는 코드에서 제거함 |
| Mac 에서 Windows 신원으로 바꿔도 macOS 신원과 같은 결과였다 (405 → 사람이 풀면 200, 재접속 200) | 1회 시험함. 필터·정렬·여러 페이지는 Windows 신원으로 시험하지 않음 | 인스턴스마다 신원을 다르게 줄 수단이 생김 (3.1, 3.4). 기본값으로 삼지는 않는다 |
| 같은 IP 에서 서로 다른 프로필이 각자 통과 상태를 가질 수 있다 | 같은 날 직접 연결에서 프로필 2개가 각각 200. 번갈아 실행했고 동시 실행은 하지 않음 | 프로필은 서로 독립된 단위로 관리한다. 동시 실행은 2단계에서 확인 |
| 가격 필터와 정렬을 한 페이지에서 이어서 쓰면 차단된다 | 시험함 | API도 둘의 동시 지정은 로컬 필터로 처리한다 |
| 고정 IP 프록시(계정 인증 SOCKS5, 로컬 중계 경유) 2개에서 1페이지 수집이 된다 | 2026-11-27 시험. 30분 간격 확인에서 7시간 넘게 200 유지. 18:16 부터 10분 간격으로 줄여 월요일까지 진행 중 | 프록시 1개 = 프로필 1개 구조를 유지한다 |
| 같은 프록시에서 통과 직후 2분 간격으로 접속하면 보안 확인이 재발했고, 가격 필터와 정렬 요청은 차단(418)됐다 | 각 1회 시도. 출구 IP 는 바뀌지 않았다. 간격을 둔 뒤에는 다시 시도하지 않음 | 통과 직후에는 간격을 길게 둔다. 필터·정렬·여러 페이지는 재시험 뒤에 넣는다 (Q1, Q11) |
| 짧은 시간에 요청이 많으면 IP 단위로 제한된다 | 차단 안내문, 시험 중 경험 | 인스턴스별 최소 간격을 강제한다 |

**아직 확인되지 않은 전제 (구현 전에 먼저 검증):**

- 고정 IP 프록시에서 필터·정렬·여러 페이지가 동작하는지. 통과 직후의 1회 시도는 차단됐다. 유지 기간 확인이 끝난 뒤 다시 시험한다 (Q11)
- 한 기기에서 Chrome 인스턴스 여러 개를 동시에 돌렸을 때의 통과율과 자원 사용량
- 프록시 경유로 여러 페이지를 받는 것 (여러 페이지는 직접 연결에서만 시험함)
- HTTP 프록시의 계정 인증이 pydoll 에서 동작하는지 (인증 SOCKS5 는 로컬 중계로 동작하는 것을 확인했다)
- 같은 기기의 인스턴스들은 IP만 다르고 브라우저 신원(핑거프린트)이 같다. 이것이 판정에 영향을 주는지
- 안전한 요청 간격과 통과 상태의 유효 기간
- Windows 실기기에서의 동작. 운영 기기를 Windows PC 로 정했으므로 옮기기 전에 반드시 확인한다 (Q2)
- 인스턴스 하나의 안전한 요청 간격. 확인된 것은 30분 간격은 7시간 넘게 문제없고 통과 직후 2분 간격은 재발한다는 것뿐이다.
  10분 간격은 2026-11-27 18:16 부터 확인 중이다 (Q20)

## 3. 구조

### 3.0 단순화 원칙

유지보수하는 사람과 나중에 코드를 고칠 개발자를 기준으로, 아래를 설계 전체에 적용한다.

1. **설정 파일은 하나.** `config.toml` 하나에 인스턴스, 전달(Slack·Telegram), API 설정을 모두 둔다 (3.1).
2. **구성 요소를 줄인다.** 배정기를 따로 두지 않는다. 워커가 작업 표에서 직접 다음 작업을 가져간다 (3.3).
3. **상태를 줄인다.** 인스턴스의 휴식과 냉각은 모두 "이 시각 이후에 다시 일함"이라는 값 하나로 표현한다 (3.2).
4. **표는 하나.** DB에는 `jobs` 표 하나만 둔다. 인스턴스 상태는 메모리에 두고 재시작하면 처음부터 다시 잡는다.
5. **의존성을 늘리지 않는다.** 표준 라이브러리(`sqlite3`, `tomllib`, `logging`)와 이미 쓰는 `aiohttp`, `pydoll`만 쓴다.
6. **쓰지 않는 것은 뺀다.** 시험 결과 쓸 수 없거나 쓰지 않는 코드는 엔진으로 가져가지 않는다 (3.5).
7. **네이버에 묶인 것은 한 파일에.** 선택자, URL, 응답 구조 해석은 `naver.py` 한 곳에 모은다. 네이버가 화면을 바꾸면 이 파일만 고친다.
8. **첫 버전에 넣지 않는 것을 정해 둔다.** 웹훅, 요청 대기(`wait`), 중복 방지 키, 다중 프로세스, 다중 기기 분산은 첫 버전에서 뺀다. 필요가 확인되면 추가한다.

```
외부 호출자 ──HTTP──▶ API 서버 ──▶ jobs 표 (SQLite) ◀── 워커 1 (프록시 A, 프로필 A)
                                     │                ◀── 워커 2 (프록시 B, 프로필 B)
                                     ▼                ◀── 워커 N (프록시 N, 프로필 N)
                              결과·원본 파일                    │
                                                    보안 확인 ──▶ Slack 또는 Telegram (한 번에 한 건)
```

한 프로세스 안에서 asyncio로 돌린다. 기존 `naver_products.py`의 접속·추출 로직을 쓰되, **지금 코드는 그대로 불러 쓸 수 없다.** 오류를 `SystemExit`로 알리고, 진행 상황을 `print`로 찍고, 보안 확인 줄 세우기를 파일 잠금으로 하기 때문이다. 이를 고치는 것이 1단계다 (6장).

### 3.1 설정 파일 (하나)

처음 계획은 인스턴스 설정(`instances.toml`)과 토큰(`.env`)을 나눴다. 나눌 이유가 없어 **`config.toml` 하나로 합친다.**
프록시 주소에 이미 계정이 들어 있어 인스턴스 설정도 비밀 정보이므로, 파일을 나눠도 보안상 얻는 것이 없고 관리할 파일만 늘어난다.

```toml
# config.toml  (git 제외, 권한 600). 저장소에는 값이 빈 config.example.toml 을 둔다.

[engine]
min_interval_seconds = 90     # 한 인스턴스가 작업 사이에 쉬는 최소 시간
jitter_seconds = 30           # 간격에 더하는 무작위 시간
launch_gap_seconds = 20       # Chrome 을 띄우는 시점 사이의 최소 간격 (순차 기동, 3.2)
max_pages = 5
retention_hours = 24          # 결과와 원본을 보관하는 시간 (Q17)
data_dir = "data"             # 프로필, DB, 결과 파일이 모이는 폴더

[api]
host = "10.0.0.5"             # 사내망 주소. 같은 기기에서만 쓸 때는 127.0.0.1 (Q7)
port = 8080
key = "…"
allow_ips = ["10.0.0.20"]     # 호출을 허용할 서버의 IP (Q18)

[relay]
use = "slack"                 # "slack" 또는 "telegram". 전환은 사람이 이 값을 바꿔서 한다 (Q19)

[slack]
bot_token = "xoxb-…"
channel_id = "C…"

[telegram]                    # Slack 장애 때의 대안. 쓰지 않으면 비워 둔다
bot_token = ""
chat_id = ""

[[instance]]
name = "kr-01"
proxy = "socks5://user:pass@host1:port"

[[instance]]
name = "kr-02"
proxy = "socks5://user:pass@host2:port"
identity = "windows"          # 생략하면 실행 기기의 OS 를 따른다 ("macos" 또는 "windows")
```

위 주소와 값은 형식을 보이기 위한 예시다.

- **인스턴스 수 = `[[instance]]` 블록 수.** 프록시를 추가하려면 블록 하나를 더 쓰면 된다.
- 설정을 읽는 코드는 한 곳(`config.py`)에 두고, 시작할 때 한 번 읽어 검증한다. 빠진 값이나 형식 오류는 어느 항목인지 알려 주고 시작하지 않는다.
- `.env`와 환경 변수 방식은 없앤다. 지금의 단독 실행 CLI도 같은 `config.toml`을 읽게 바꾼다.
- `tomllib`은 Python 3.11부터 표준 라이브러리다. 지원 버전을 3.10 이상에서 **3.11 이상**으로 올린다 (지금 개발 환경은 3.12).
- 프로필 폴더는 `data/profiles/<name>/`으로 자동 배정한다. 이름과 프록시, 신원의 짝은 바꾸지 않는다 (IP 하나에 프로필 하나). 짝이 바뀌었는지는 시작할 때 검사한다 (3.4).
- 프록시 없이 직접 연결하는 인스턴스도 하나 둘 수 있다 (`proxy = ""`).
- 시작할 때 프록시마다 출구 IP를 확인해, 서로 겹치거나 한국 IP가 아니면 그 인스턴스를 띄우지 않는다. 운영 중에도 주기적으로 다시 확인해 바뀌었으면 중지한다.
- **프록시 인증**:
  - 계정 인증이 있는 SOCKS5: Chrome 이 지원하지 않으므로 pydoll 의 `SOCKS5Forwarder`(로컬 중계)를 인스턴스마다 하나씩 띄운다.
    Chrome 은 인증 없는 `127.0.0.1` 의 중계로 붙고, 중계가 대신 인증한다. 지금 쓰는 프록시 2개가 이 방식이고, 실제로 동작하는 것을 확인했다.
    중계마다 로컬 포트가 하나씩 필요하다 (3.2 의 포트 항목).
  - HTTP/HTTPS 프록시: 주소에 `user:pass@`를 넣으면 pydoll이 계정을 떼어 내고 인증 요청에 대신 응답한다 (소스에서 확인, 실제 프록시로는 시험하지 않음).
- **시작 규모**: 인스턴스 2개로 시작한다 (Q3). 늘리는 것은 인스턴스 하나의 안전한 간격을 잰 뒤, 필요한 처리량에 맞춰 정한다 (Q16, Q20).

### 3.2 워커 (인스턴스 1개)

인스턴스가 기억하는 값은 세 가지뿐이다.

| 값 | 의미 |
| --- | --- |
| `busy` | 지금 작업 중인지 |
| `available_at` | 이 시각 이후에 다음 작업을 가져갈 수 있음. 작업 뒤 휴식이든 차단 뒤 냉각이든 이 값만 뒤로 민다 |
| `disabled_reason` | 비어 있지 않으면 중지 상태. 사유를 그대로 적는다 |

워커의 동작은 한 개의 반복문이다: "쉴 시간이 지났으면 작업 하나를 가져온다 → 처리한다 → `available_at`을 민다."
보안 확인을 기다리는 것은 인스턴스 상태가 아니라 작업의 상태(`waiting_human`)로만 표시한다.

- **작업 처리**: 작업마다 Chrome을 띄우고 끝나면 닫는다 (지금 검증된 방식 그대로). 닫은 뒤 프로필 캐시를 정리한다.
- **간격**: 작업이 끝나면 `min_interval + 무작위`만큼 쉰다.
- **순차 기동**: 인스턴스들은 동시에 뜨지 않고 하나씩 차례로 뜬다.
  - 엔진 전체에 "기동 차례" 잠금 하나(`asyncio.Lock`)를 둔다. 워커는 Chrome 을 띄우기 전에 이 잠금을 잡고,
    Chrome 이 떠서 신원 적용까지 끝나면 놓는다. 잠금을 놓은 뒤 `launch_gap_seconds`(+ 무작위)가 지나야 다음 워커가 잡을 수 있다.
  - 이 규칙 하나가 세 경우를 모두 처리한다: 엔진을 처음 켤 때, 재시작 뒤 밀린 작업이 한꺼번에 풀릴 때,
    운영 중 여러 워커의 휴식이 같은 시각에 끝날 때.
  - 엔진을 켤 때의 사전 점검(출구 IP 확인, 짝 검사)과 `engine onboard` 도 인스턴스 순서대로 하나씩 한다.
  - 차례를 기다리는 시간에도 상한을 둔다. 넘으면 그 작업을 `queued` 로 되돌린다.
  - 이유: Chrome 여러 개가 같은 순간에 뜨면 기기의 CPU·메모리 사용이 몰리고, 같은 기기에서 나가는 첫 요청들이
    같은 시각에 겹친다. 인스턴스가 N 개면 모두 뜨는 데 약 `N × launch_gap_seconds` 가 걸린다 (10개, 20초면 약 3분).
  - 작업 처리 자체는 계속 동시에 한다. 줄을 세우는 것은 띄우는 구간뿐이다.
- **보안 확인(405)**: 설정에서 고른 메신저(기본 Slack)로 전달한다. 메시지에 인스턴스 이름을 붙이고, 전체에서 한 번에 한 건만 나간다. 통과하면 작업을 이어 간다.
  - 브라우저 창에서 사람이 직접 푸는 경로는 두지 않는다. 엔진과 단독 실행 명령 모두 메신저 전달만 쓴다 (Q9).
  - Slack 이 실패해도 Telegram 으로 자동 전환하지 않는다. 같은 문제가 두 곳에 가면 답이 엇갈릴 수 있다. 전환은 사람이 설정을 바꿔서 한다 (Q19).
  - 한 프로세스 안에서는 지금의 파일 잠금 대신 `asyncio.Lock`으로 줄을 세운다. 파일 잠금은 20분이 지나면 남의 잠금을 가져가므로 사람 응답을 오래 기다릴 때 두 건이 동시에 나갈 수 있고, 엔진이 죽으면 잠금이 남는다.
  - 차례를 기다리는 동안 작업 상태는 `waiting_human`이고, 차례 대기에도 시간 제한을 둔다.
  - 메신저 호출이 실패하면 그 작업만 `failed`로 끝내고 인스턴스는 `보안 확인 필요` 상태로 둔다.
- **차단(418)**: 그 인스턴스를 냉각 상태로 둔다 (예: 10분 → 30분 → 2시간으로 늘림). 작업은 큐로 돌려보내 다른 인스턴스가 처리한다. 연속 3회 차단이면 중지하고 Slack으로 알린다.
- **프로세스 격리**: 워커가 띄운 Chrome이 남지 않도록 종료를 확인하고, 엔진 시작 시 이전 실행의 잔여 Chrome을 정리한다. 정리 대상은 프로세스 명령줄의 `--user-data-dir`이 자기 프로필 경로와 일치하는 것만으로 한정한다 (PID만으로 판단하지 않는다).
- **CDP 포트 (WebSocket)**: 인스턴스마다 Chrome이 따로 뜨고, 각 Chrome은 자기 디버깅 포트 하나를 연다. pydoll은 이 포트로 WebSocket을 맺는다. 포트가 겹치면 새 Chrome이 포트를 못 잡고 pydoll이 **다른 인스턴스의 브라우저를 제어하게 되는** 것이 위험이다.
  - pydoll 3.0.1의 동작 (소스에서 확인): Chrome 객체를 만들 때 운영체제에 빈 포트를 물어 받아 두고, 실제로 띄우기 직전에 그 포트가 여전히 비어 있는지 다시 확인한다. 이미 쓰이고 있으면 띄우지 않고 오류(`FailedToStartBrowser`)를 낸다. 즉 겹치더라도 조용히 남의 브라우저를 잡는 대신 실패한다.
  - 시험 결과: 포트를 10개씩 연달아 고르는 것을 2,000회 반복해 중복 0회. Chrome 8개를 동시에 띄우는 것을 3회 반복해 24개 모두 서로 다른 포트로 떴고, 각자 자기 브라우저를 제어하는 것을 확인했다 (외부 접속 없는 페이지로 시험).
  - 남는 틈: 포트를 고른 시점과 Chrome이 그 포트를 잡는 시점 사이에 다른 프로그램이 같은 포트를 가져갈 수 있다. 시험에서는 발생하지 않았지만 없다고 할 수는 없다.
  - 대응: 기동 시 `FailedToStartBrowser`가 나면 새 포트로 다시 띄운다 (횟수 제한). 더 확실히 하려면 인스턴스마다 포트를 설정에서 고정 배정한다 (pydoll의 `connection_port` 인자). 기동 직후 브라우저가 자기 프로필 경로로 떴는지 확인하는 검사를 넣으면 잘못 연결된 경우도 잡을 수 있다.
  - 같은 주의가 SOCKS5 로컬 중계에도 적용된다. 중계마다 로컬 포트가 하나씩 필요하므로 인스턴스별로 겹치지 않게 배정한다.
- **기록**: `print` 대신 인스턴스 이름이 붙는 로그를 쓴다. 프로필 캐시 정리를 건너뛴 경우도 로그와 수치에 남긴다.
- **중지 사유**: 인스턴스가 중지되면 사유(연속 차단, 프록시 장애, 출구 IP 변경, 디스크 부족 등)를 상태에 남기고 Slack으로 알린다.

### 3.3 작업 가져가기 (배정기 없음)

배정기를 따로 두지 않는다. **`jobs` 표가 곧 큐**이고, 각 워커가 쉴 시간이 지나면 직접 가장 오래된 `queued` 작업 하나를 가져간다.

- 가져가는 동작은 "`queued`인 가장 오래된 행을 `running`으로 바꾸고 인스턴스 이름을 적는다"는 한 문장의 갱신이다.
  SQLite 쓰기는 한 번에 하나만 실행되므로 두 워커가 같은 작업을 가져가지 않는다.
- 쉬고 있던 워커가 먼저 가져가므로, 누가 처리할지 고르는 별도 로직이 필요 없다.
- `queued` 작업 수에 상한을 두고 넘으면 API가 거절(429)한다.
- 실패한 작업은 시도 횟수를 올리고 `queued`로 되돌린다. 최대 2회. 차단(418)으로 실패했으면 "이 시각 이후에 다시 시도" 값을 함께 적어 바로 다른 인스턴스로 넘어가지 않게 한다 (같은 요청을 여러 IP에서 연달아 보내면 차단을 넓힐 수 있다는 추정).

### 3.4 프로필 관리

여러 프로필로 운영할 때 실제로 관리해야 하는 것은 프로필이다. 사람이 통과시킨 보안 확인 상태가 프로필 폴더에만
들어 있고, 다시 만들려면 사람 손이 필요하기 때문이다.

#### 원칙

1. **프로필 하나는 출구 IP 하나, 신원 하나에 묶는다.** 통과 상태가 IP 나 신원이 바뀌어도 유지되는지는 확인한 적이 없다. 모르는 것은 바꾸지 않는다.
2. **프로필을 복제하지 않는다.** 통과된 프로필을 복사해 여러 인스턴스에 나눠 주면 같은 쿠키가 여러 IP 에서 동시에 쓰인다.
   한 프로필이 판정되면 사본이 함께 판정될 수 있다 (추정, 시험하지 않음). 프로필은 인스턴스마다 따로 만들어 따로 통과시킨다.
3. **프로필 하나에는 Chrome 을 하나만 띄운다.** 인스턴스 하나가 한 번에 작업 하나만 처리하므로 구조상 지켜진다.
4. **프로필을 다른 OS 로 옮기지 않는다.** 쿠키가 OS 별로 암호화되어 옮기면 통과 상태가 사라진다.
5. **출구 하나에 프로필을 둘 이상 두지 않는다.** 차단이 IP 단위로 걸리므로 처리량이 늘지 않고 판정 위험만 는다. 시작할 때 출구가 겹치는 인스턴스는 띄우지 않는다 (3.1).

#### 폴더 구성

```
data/
  profiles/
    kr-01/
      chrome/            Chrome 의 user-data-dir (쿠키, 통과 상태)
      instance.json      이 프로필의 고정 정보와 이력 (아래)
    kr-02/
      ...
  cache/kr-01/           디스크 캐시. 프로필 밖에 두어 언제든 지울 수 있다
  jobs.sqlite            작업 표
  results/               결과 JSON 과 원본
```

`instance.json` 은 엔진이 쓰는 작은 파일이다. DB 표를 늘리지 않으려고 프로필 폴더에 둔다.

| 항목 | 용도 |
| --- | --- |
| `identity` | 프로필을 만들 때의 신원. 설정과 다르면 그 인스턴스를 띄우지 않는다 |
| `exit_ip` | 등록 때 확인한 출구 IP. 달라졌으면 띄우지 않고 알린다 |
| `created_at`, `onboarded_at` | 만든 시각, 처음 통과한 시각 |
| `last_ok_at`, `last_captcha_at`, `last_blocked_at` | 마지막 정상·보안 확인·차단 시각. 통과 상태의 수명을 재는 근거 |
| `captcha_count`, `blocked_count` | 누적 횟수 |

설정 파일을 고치다가 이름은 그대로 두고 프록시나 신원만 바꾸는 실수를 이 파일로 잡는다.
짝을 바꾸고 싶으면 새 이름으로 인스턴스를 만들어 새로 통과시킨다.

#### 프로필의 수명

```
(없음) ──등록──▶ 사용 가능 ──보안 확인 재발──▶ 사람 대기 ──통과──▶ 사용 가능
                    │                                  └─실패·시간 초과─▶ 중지
                    └──연속 차단·출구 IP 변경·짝 불일치──▶ 중지
```

이 그림은 설명용이다. 코드에 상태 값을 따로 두지 않는다. 3.2의 세 값(`busy`, `available_at`, `disabled_reason`)과
작업 상태 `waiting_human` 으로 모두 표현된다.

- **등록** (`engine onboard`): 통과 기록이 없는 인스턴스를 **하나씩 순서대로** 띄워 보안 확인을 Slack 으로 통과시킨다.
  통과하면 `instance.json` 에 기록한다. 이미 통과한 인스턴스는 건너뛴다. 한 번에 한 건만 Slack 에 나가므로
  인스턴스가 많아도 담당자는 차례대로 답하면 된다.
- **재발**: 운영 중 405 가 나오면 같은 전달 절차가 그 작업 안에서 돈다 (3.2). 별도 명령이 필요 없다.
- **확인** (`engine check`): 작업이 없을 때 인스턴스를 띄워 검색 한 번으로 통과 상태를 확인하는 명령. 자동 주기 실행은
  첫 버전에 넣지 않는다. 요청을 늘리는 일이라, 필요한지는 통과 상태의 수명을 잰 뒤에 정한다.
- **폐기와 교체**: 중지된 인스턴스는 자동으로 되살리지 않는다. 사람이 원인을 본 뒤 프로필 폴더를 지우고 다시 등록하거나,
  새 이름으로 교체한다. 폴더 삭제는 명령(`engine remove <name>`)으로만 하고, 지우기 전에 Chrome 이 떠 있지 않은지 확인한다.
- **추가**: `config.toml` 에 `[[instance]]` 블록을 더하고 `engine onboard` 를 실행한다. 엔진 재시작이 필요하다
  (실행 중 설정 다시 읽기는 첫 버전에 넣지 않는다).

#### 브라우저 신원 배정

- **Mac 에서 돌리는 동안은 macOS 신원과 Windows 신원을 절반씩 쓴다 (Q4).** 지금의 두 프로필이 이미 그렇게 되어 있다
  (kr01 은 macOS, kr02 는 Windows). 인스턴스의 `identity` 로 지정한다.
- **Windows PC 로 옮기면 모두 Windows 신원으로 한다 (Q15).** 실제 기기와 신원이 일치한다.
  Windows PC 에서 macOS 신원을 쓰는 조합은 시험한 적이 없고 쓰지 않는다.
- Mac 에서의 Windows 신원은 신원과 실제 환경(폰트 폭, GPU)이 어긋난 상태다. 통과와 7시간 유지는 확인했지만
  필터·정렬·여러 페이지는 이 신원으로 시험하지 않았다.
- 신원은 프로필을 만들 때 정하고 바꾸지 않는다. Chrome 버전은 실제 Chrome 을 따라가므로 자동 업데이트되면
  모든 프로필의 UA 버전이 함께 올라간다 (실제 사용자의 브라우저와 같은 동작).
- 지금 코드는 환경 변수 `FINGERPRINT_OS` 로 신원을 고른다. 한 프로세스에서 인스턴스마다 다르게 주려면
  함수 인자로 넘기도록 1단계에서 바꾼다.

#### 잠금과 남은 프로세스

- 작업을 시작하기 전에 그 프로필로 떠 있는 Chrome 이 없는지 확인한다. 지금 코드의 `profile_in_use()` 가 이 일을 한다
  (잠금에 적힌 프로세스가 실제로 살아 있을 때만 사용 중으로 본다).
- Chrome 이 비정상 종료해 잠금 파일만 남은 경우는 Chrome 이 스스로 넘겨받는다. 같은 기기에서 계속 실행하므로
  컨테이너에서 겪은 "다른 컴퓨터에서 사용 중" 거부는 생기지 않는다.
- 엔진 시작 시의 잔여 Chrome 정리는 3.2 에 적은 대로 자기 프로필 경로와 일치하는 것만 대상으로 한다.

#### 용량

- 디스크 캐시는 프로필 밖(`data/cache/<name>/`)에 두고 상한을 건다. 작업이 끝날 때마다 프로필 안의 캐시 폴더를 지운다.
  지금 코드에 이미 들어 있고, 프로필 하나가 약 144MB 에서 더 늘지 않는 것을 확인했다.
- 처음 만든 프로필은 캐시와 내려받은 구성 요소를 지우면 약 9MB 까지 줄고 통과 상태는 유지됐다.
  Chrome 의 구성 요소 내려받기를 끄는 실행 옵션을 엔진에 넣을지는 2단계에서 인스턴스 수를 보고 정한다.
- 인스턴스별 프로필 크기를 `/v1/instances` 에 넣고, 기준을 넘으면 알린다.

#### 백업

통과 상태를 잃으면 사람이 다시 풀어야 하므로 프로필 폴더는 백업할 가치가 있다. 다만 복원한 프로필이 통과 상태를
유지하는지는 시험하지 않았다. 첫 버전에는 백업 기능을 넣지 않고, 필요하면 엔진을 멈춘 상태에서 `data/profiles/` 를
통째로 복사한다 (같은 기기, 같은 OS 계정에서만 복원 가능).

### 3.5 코드 구성

지금 코드는 시험하면서 기능을 붙여 나간 스크립트라 역할이 섞여 있다 (4개 파일, 약 2,200줄. 그중 860줄은 핑거프린트 값).
엔진으로 가면서 역할별로 나누고, 쓰지 않는 것은 뺀다.

| 파일 | 역할 | 지금 코드에서 |
| --- | --- | --- |
| `config.py` | `config.toml` 읽기와 검증 | 새로 작성. `.env` 읽기 코드를 대체 |
| `browser.py` | Chrome 띄우기, 신원 적용, 프로필 캐시 정리 | `stealth_visit.py`에서 옮김 |
| `fingerprints.py` | 브라우저 신원 값 (데이터) | 그대로. Linux 값은 이미 뺌 |
| `naver.py` | 네이버 전용: 검색 열기, 필터, 정렬, 페이지 이동, 응답 해석, 보안 확인 화면 조작 | `naver_products.py`에서 옮김 |
| `relay.py` | 보안 확인을 메신저(Slack, Telegram)로 전달 | `human_relay.py`에서 Slack 과 Telegram 부분. `dialog` 는 뺌 |
| `engine.py` | 워커 반복문, `jobs` 표 | 새로 작성 |
| `api.py` | HTTP 엔드포인트 | 새로 작성 |
| `cli.py` | 명령: 단독 실행, 인스턴스 등록, 서버 실행 | 지금의 CLI를 정리 |

의존 방향은 한쪽으로만 흐른다: `api` → `engine` → `naver` → `browser`. `naver.py`는 엔진이나 API를 모른다.
그래서 `naver.py`의 함수 하나(`search(tab, 조건) → 결과`)는 엔진 없이 CLI나 시험에서 그대로 부를 수 있다.

**오류는 네 가지 예외로만 알린다**: `Blocked`(418), `CaptchaFailed`, `RelayFailed`, `ParseError`.
엔진은 예외 종류만 보고 처리(냉각, 재시도, 실패)를 정한다. 메시지 문자열을 해석하지 않는다.

**엔진으로 가져가지 않는 것** (시험 기록은 README에 남긴다):

| 대상 | 이유 |
| --- | --- |
| Docker 이미지, Linux 신원, 컨테이너용 전달 방식(`file`) | **제거함 (2026-11-27).** Linux 는 쓸 수 없음이 확인됨 |
| 시험용 전달 방식 (`dialog`) | 연동 전 시험을 위한 것. 역할이 끝남 (Q8) |
| 브라우저 창에서 직접 푸는 대기 흐름, 헤드리스에서 창 표시 모드로 다시 여는 로직 | 보안 확인은 메신저 전달로 통일한다. 단독 실행 명령에서도 뺀다 (Q9) |
| `--turnstile` 옵션 | 네이버에서 쓰이지 않고 실행해 본 적도 없음 |
| 출구 IP가 바뀌는 프록시 지원 | 필터가 차단됨. 고정 IP만 지원 |

Windows 신원은 남긴다. 운영 기기가 Windows PC 이고, Mac 에서도 인스턴스별 신원으로 쓴다 (3.4).
Telegram 전달은 Slack 장애 때의 대안으로 남긴다 (Q8). 실제 봇으로 써 본 적이 없으므로 1단계에서 1회 시험한다 (Q19).

**시험은 세 층으로 둔다.**

- `naver.py`의 응답 해석: 저장해 둔 실제 응답 파일로 오프라인 시험. 네이버가 구조를 바꾸면 여기서 먼저 깨진다.
- `relay.py`: 지금 있는 가짜 서버 시험.
- `engine.py`: 브라우저 대신 가짜 `search` 함수를 넣어 휴식, 냉각, 재시도, 재시작 복구를 시험. 실제 접속 없이 돈다.

## 4. 외부 API

`aiohttp.web`으로 만든다 (이미 쓰고 있는 의존성이라 추가 설치가 없다).

### 4.1 엔드포인트

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/v1/search` | 검색 작업 등록. 작업 ID 반환 (202) |
| GET | `/v1/jobs/{id}` | 작업 상태와 결과 JSON |
| GET | `/v1/jobs/{id}/source` | 원본 (아래 4.3) |
| GET | `/v1/instances` | 인스턴스별 상태 (대기, 작업 중, 냉각 등) |
| GET | `/healthz` | 서버 생존 확인 |

요청 한 건이 15초~수 분(보안 확인 대기 포함) 걸리므로 **등록 후 조회 방식** 하나만 둔다.
호출자는 작업 ID를 받아 `GET /v1/jobs/{id}`를 주기적으로 조회한다. 응답을 붙잡고 기다리는 방식과 웹훅은 넣지 않는다 (Q6).

**수집 범위 (Q1, Q11, Q12)**: 여러 페이지, 가격 필터, 정렬을 모두 지원하는 것이 목표다. 다만 프록시에서 확인된 것은 1페이지 수집뿐이므로,
유지 기간 확인이 끝난 뒤 같은 프로필로 다시 시험해서 통과한 기능만 넣는다. 다시 막히는 기능은 빼고 진행한다:
가격 조건은 받은 목록에서 거르고, 정렬은 지원하지 않는다.

### 4.2 요청과 응답

```json
POST /v1/search
{
  "query": "LG 그램 16인치 5060",
  "product_set": "model",
  "min_price": 2000000,
  "max_price": 3000000,
  "sort": "rank",
  "pages": 2,
  "include_source": false
}
```

```json
GET /v1/jobs/{id}
{
  "id": "…", "status": "done",
  "instance": "kr-01",
  "requested_at": "…", "finished_at": "…",
  "result": { "query": "…", "total": 130, "count": 80, "products": [ … ] },
  "source_url": "/v1/jobs/{id}/source"
}
```

- `status`: `queued`, `running`, `waiting_human`, `done`, `failed`.
- `result`는 지금 `products.json`과 같은 형식이다.
- `sort`와 가격 필터를 함께 주면 지금처럼 정렬은 서버에서, 가격은 받은 목록에서 거른다. 응답에 `price_filter: "local"`로 표시한다.
- 실패 시 `error`에 사유를 넣는다: `blocked`(418), `captcha_timeout`, `relay_failed`, `parse_error`, `no_instance`, `invalid_request`.
- 입력 검증: `query` 길이, `pages` 상한, `min_price > max_price` 등은 `invalid_request`로 바로 거절한다.
- 중복 등록 방지 키(`Idempotency-Key`)는 첫 버전에 넣지 않는다. 호출자가 응답을 못 받아 같은 요청을 다시 보내면 작업이 두 번 돈다. 이것이 실제로 문제가 되면 추가한다.

### 4.3 원본(source)의 정의

"source"는 **네이버가 내려준 가공 전 데이터**로 정한다 (Q5).

- 첫 페이지: 문서 HTML 전체 (`__NEXT_DATA__` 포함)
- 필터·정렬·2페이지 이후: 검색 API(`/api/search/all`) 응답 JSON 원문
- `GET /v1/jobs/{id}/source`는 이를 페이지 순서대로 담은 JSON(`[{page, kind: "html"|"api", body}]`)으로 돌려준다.

화면에 그려진 뒤의 DOM 은 돌려주지 않는다.

- `include_source`의 기본값은 `false`다. 원본은 요청한 경우에만 보관한다.
- 원본은 크므로 응답 크기에 상한을 두고 gzip으로 보낸다.
- 원본에 요청 측 정보(쿠키, 세션 값, 지역 정보 등)가 섞여 있는지 구현 전에 확인하고, 있으면 제거한다 (아직 확인하지 않음).
- 제3자 사이트의 원문을 외부 호출자에게 다시 전달하는 것이므로, 0단계의 약관·법적 검토 범위에 "원본 재전송"을 포함한다.

### 4.4 저장

- 표는 `jobs` 하나다 (id, 상태, 요청 내용, 인스턴스, 시도 횟수, 다음 시도 시각, 오류, 결과 경로, 원본 경로, 시각들).
- 작업 큐와 상태를 SQLite 한 파일에 둔다 (큐를 메모리에만 두면 재시작 때 대기 중인 작업이 사라진다). 결과 JSON과 원본은 크기가 커서(원본은 페이지당 수백 KB) 파일로 저장하고 DB에는 경로만 기록한다.
- `queued` → `running` 전환은 트랜잭션으로 해서 한 작업을 두 워커가 가져가지 않게 한다.
- 보관 기간은 24시간이다 (Q17). 지나면 DB의 행과 결과·원본 파일을 함께 지운다. 디스크 여유가 기준 아래로 내려가면 새 작업을 거절한다.
- 엔진이 재시작되면 `running`이던 작업은 재시도 횟수가 남아 있으면 `queued`로 되돌리고, 아니면 `failed`로 바꾼다.

#### SQLite 파일 크기 관리

SQLite는 행을 지워도 파일이 줄지 않는다. 지운 자리는 파일 안의 빈 페이지로 남아 다음 쓰기에 재사용될 뿐이다.
보관 기간이 지난 작업을 계속 지우는 구조이므로, 아래를 처음부터 설계에 넣는다.

- **큰 데이터를 DB에 넣지 않는다.** 원본은 이미 파일로 빼 두었다. 결과 JSON도 작업당 수백 KB가 될 수 있으므로
  (2페이지 80개가 약 170KB) 파일로 저장하고 DB에는 상태, 시각, 경로 같은 작은 값만 둔다.
  DB가 작게 유지되면 아래 정리 작업의 부담도 작아진다.
- **`auto_vacuum = INCREMENTAL`을 DB를 만들 때 켠다.** 이 설정은 테이블을 만들기 전에 지정해야 하고,
  이미 만든 DB에 적용하려면 전체 `VACUUM`을 한 번 돌려야 한다. 켜 두면 `PRAGMA incremental_vacuum(N)`으로
  빈 페이지를 조금씩 반납할 수 있다. 보관 기간 정리 직후에 함께 실행한다.
  - 주의: Python에서 이 PRAGMA는 실행 결과를 끝까지 읽어야(`.fetchall()`) 실제로 반납된다. 실행만 하고 결과를 읽지 않으면 파일이 줄지 않는다.
  - 확인한 수치 (SQLite 3.53): 10MB를 넣고 모두 지운 뒤에도 파일은 10MB 그대로였고, 위 방식으로 실행하자 12KB로 줄었다.
- **전체 `VACUUM`은 예외적으로만 쓴다.** DB 전체를 새 파일로 다시 쓰는 작업이라 다음을 지켜야 한다.
  - 실행 중에는 다른 쓰기가 막힌다. 작업이 없는 시간에, 워커가 모두 쉬는 상태에서만 돌린다.
  - DB 크기만큼의 여유 디스크가 추가로 필요하다. 디스크가 부족할 때 돌리면 실패한다.
  - 열려 있는 트랜잭션이 있으면 실행되지 않는다.
  - 실행 조건을 수치로 정한다. 예: 빈 페이지 비율(`PRAGMA freelist_count` ÷ `PRAGMA page_count`)이 30%를 넘고
    DB 크기가 기준(예: 200MB)을 넘을 때만.
- **WAL 파일도 따로 커진다.** 동시 읽기·쓰기를 위해 WAL 모드를 쓰면 `-wal` 파일이 생기는데,
  오래 열려 있는 읽기 연결이 있으면 정리되지 않고 계속 커진다.
  `journal_size_limit`로 상한을 두고, 정리 시점에 `PRAGMA wal_checkpoint(TRUNCATE)`를 실행한다.
  읽기 연결은 오래 열어 두지 않는다.
- **쓰기는 한 곳에서만 한다.** SQLite는 동시에 쓰는 연결이 하나뿐이다. 워커 여러 개가 각자 쓰면 잠금 대기가 생기므로,
  쓰기는 전용 스레드 하나로 모으고 `busy_timeout`을 설정한다. SQLite 호출은 블로킹이므로 asyncio 루프에서 직접 부르지 않는다.
- **크기를 지켜본다.** DB 파일 크기, WAL 파일 크기, 빈 페이지 비율을 4단계의 운영 수치에 넣고,
  기준을 넘으면 Slack으로 알린다.
- **백업은 파일 복사로 하지 않는다.** 쓰는 중인 DB 파일을 그대로 복사하면 깨진 사본이 나올 수 있다.
  SQLite의 백업 기능(`VACUUM INTO` 또는 backup API)을 쓴다.

이 구조에서 DB에 남는 것은 작업당 수백 바이트 수준의 행이므로, 하루 수천 건을 처리해도 DB가 크게 자랄 가능성은 낮다.
그래도 정리 주기와 실행 조건을 정해 두지 않으면 나중에 운영 중에 전체 `VACUUM`을 돌려야 하는 상황이 생긴다.
위 수치(30%, 200MB)는 예시이며 실제 사용량을 보고 정한다.

### 4.5 보안

- 호출하는 쪽은 사내망의 다른 서버다 (Q7). API 서버는 사내망 주소에 바인딩한다. 인터넷에는 열지 않는다.
- 인증은 두 겹이다 (Q18): `Authorization: Bearer <API 키>` 와 호출 서버의 IP 허용 목록. 둘 다 `config.toml`의 `[api]`에 둔다.
  허용 목록에 없는 IP 의 요청은 키가 맞아도 거절한다.
- 통신은 사내망 평문(HTTP)이다. 응답에 상품 목록과 원본이 실리므로, 망 구성이 바뀌어 신뢰할 수 없는 구간을 지나게 되면 TLS 를 추가한다.
- 키별 요청 수 제한, 요청 본문 크기 제한, `pages` 상한.
- 입력값(`query` 등)은 브라우저에 타이핑하거나 URL 인코딩하는 데만 쓰고, 셸이나 스크립트에 끼워 넣지 않는다.
- 프록시 인증 정보와 Slack 토큰은 API 응답과 로그에 나오지 않게 한다. `/v1/instances`는 프록시 주소를 가려서 보여 준다.

## 5. 처리량 가늠

인스턴스 하나가 작업 하나에 약 30~60초(2페이지 기준, 측정하지 않은 어림값)를 쓰고 90~120초를 쉰다고 하면, 인스턴스당 시간당 20~30건이다.
프록시 10개면 시간당 200~300건 수준이다. **이 간격이 안전한지는 확인되지 않았다.** 대규모 시험에서 조정해야 한다.

위 수치는 가정이다. 지금 확인된 것은 인스턴스 하나가 30분에 한 번(시간당 2건) 접속할 때 7시간 넘게 문제가 없었다는 것과,
통과 직후 2분 간격의 접속에서 보안 확인이 재발했다는 것뿐이다. 필요한 처리량과 인스턴스 수는 인스턴스 하나의 안전한 간격을 잰 뒤에 정한다 (Q16, Q20).

Chrome 인스턴스 하나의 메모리 사용량은 측정하지 않았다. 한 기기에서 몇 개까지 돌릴 수 있는지는 2단계에서 잰다.

## 6. 단계

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 0. 선행 확인 | 이용 약관·법적 검토(원본 재전송 포함). 유지 기간 확인(2026-11-30 09:00 종료) 결과 정리. 그 뒤 같은 프록시 프로필 2개로 여러 페이지·가격 필터·정렬을 다시 시험 (Q11). 인스턴스 하나의 안전한 요청 간격 측정 (Q20) | 검토 결과가 진행 가능. 기능별로 통과·차단이 판정되어 첫 버전에 넣을 기능이 정해짐 (Q12). 최소 요청 간격의 기본값이 수치로 정해짐 |

| 3. 외부 API | 엔드포인트, 인증, 입력 검증 | API로 요청해 JSON과 원본을 받음. 인증 없는 요청과 잘못된 입력 거절. 재시작 후 대기 중이던 작업이 이어서 처리됨 |
| 4. 운영 기능 | 인스턴스별 성공률·차단률·보안 확인 횟수·캐시 정리 실패 횟수 기록, Slack 알림, 프로필 용량 관리, DB 크기 관리(보관 기간 정리, 점진적 반납, WAL 정리) | `/v1/instances`에서 인스턴스별 위 수치를 조회할 수 있음. 작업을 대량으로 넣고 지운 뒤 DB와 WAL 파일 크기가 기준 안으로 돌아오는 것을 확인 |
| 5. 규모 시험 | 검색어·요청량·기간을 늘려 측정 | 안전한 간격과 인스턴스당 처리량이 수치로 나옴 |

0단계가 통과하지 못하면 이후 단계는 진행하지 않는다.

**시작 시점 (Q10)**: 1단계를 포함한 모든 구현은 2026-11-30 의 유지 기간 결과를 본 뒤에 시작한다. 그때까지 확인 프로세스가 지금 코드로 돌고 있다.

**실행 기기 (Q2, Q13, Q14)**: 운영 기기는 사내에서 배정받는 Windows PC 다. 준비될 때까지 개발과 시험은 이 Mac 에서 한다.
Windows PC 가 준비되면 실기기 시험(새 프로필 통과, 재접속, 지원 기능)을 먼저 하고, 통과하면 옮긴다.
프로필은 OS 사이에 옮길 수 없으므로 Windows 에서는 인스턴스마다 프로필을 새로 만들어 보안 확인을 다시 통과시킨다.

## 7. 위험

| 위험 | 대응 |
| --- | --- |
| 고정 IP 프록시에서 필터·정렬이 계속 차단됨 | 0단계에서 다시 시험. 막히면 그 기능만 빼고 진행 (Q12) |
| Windows 실기기에서 결과가 다름 | 옮기기 전에 실기기 시험. 통과하지 못하면 Mac 에서 계속 운영하고 원인을 본다 |
| 인스턴스들의 브라우저 신원이 같아 한꺼번에 판정됨 | 2단계에서 인스턴스 수를 늘려 가며 관찰. 영향이 보이면 일부를 Windows 신원으로 돌려 비교 (3.4) |
| 보안 확인이 자주 재발해 담당자 부담이 커짐 | 발생 횟수를 기록. 잦으면 간격을 늘리거나 인스턴스를 줄임 |
| 네이버의 화면·API 구조 변경 | 추출 실패를 감지해 알림. 원본을 보관해 원인 파악 |
| 실행 기기가 macOS/Windows여야 함. Linux 서버와 컨테이너로 확장할 수 없음 | 사내 Windows PC 를 쓴다 (Q2). 기기당 인스턴스 수 한계를 2단계에서 측정 |
| 통과된 프로필을 잃음 (디스크 장애, 실수로 삭제) | 사람이 다시 통과시켜야 함. 삭제는 명령으로만. 백업은 3.4 |
| 이용 약관·법적 문제 | 0단계의 선행 조건. 공식 Open API로 대체 가능한 범위 검토 |
| API 키 유출로 수집 남용 | 사내망 바인딩, IP 허용 목록, 키 교체 절차, 키별 제한 |
| SQLite 파일과 WAL 파일이 줄지 않고 커짐 | 큰 데이터는 파일로 분리, 점진적 반납, WAL 상한과 정리, 크기 감시 (4.4) |

## 8. 결정 사항

2026-11-27 에 사용자가 결정 21개를 확정했다. 원문과 근거는 `docs/decisions/engine-design.md` 에 있고, 이 문서의 해당 위치에 반영했다.

| 주제 | 결정 | 반영 위치 |
| --- | --- | --- |
| 수집 범위 (Q1, Q11, Q12) | 여러 페이지·가격 필터·정렬 모두. 프록시에서 다시 시험해 통과한 것만 넣고, 막히는 기능은 뺀다 | 4.1, 6장 |
| 실행 기기 (Q2, Q13, Q14) | 사내 Windows PC. 준비 전까지는 이 Mac 에서 개발과 시험 | 6장 |
| 인스턴스 수 (Q3, Q16, Q20) | 2개로 시작. 안전한 간격을 잰 뒤 필요한 처리량에 맞춰 늘린다 | 3.1, 5장 |
| 브라우저 신원 (Q4, Q15) | Mac 에서는 macOS 와 Windows 절반씩, Windows PC 에서는 모두 Windows | 3.4 |
| 원본과 보관 (Q5, Q17) | 네이버가 내려준 가공 전 데이터. 24시간 보관 | 4.3, 4.4 |
| API (Q6, Q7, Q18) | 등록 후 조회만. 사내망의 다른 서버가 호출. API 키 + IP 허용 목록, 사내망 HTTP | 4.1, 4.5 |
| 보안 확인 전달 (Q8, Q9, Q19) | 메신저 전달로 통일. `dialog` 와 창에서 직접 풀기는 뺀다. Telegram 은 설정으로 고르는 대안 | 3.2, 3.5 |
| 구현 시작 (Q10) | 2026-11-30 유지 기간 결과를 본 뒤 | 6장 |

**아직 정하지 못한 것** (선행 결과가 나오면 결정 문서에 이어서 묻는다):

1. 인스턴스의 최소 요청 간격: 유지 기간 결과와 프록시 재시험 결과가 필요하다. 3.1 의 `min_interval_seconds = 90` 은 임시 값이다.
2. 기기당 인스턴스 상한: 메모리 사용량을 재야 한다.

## 9. 감사 결과와 반영

코드와 시험 기록을 직접 읽는 독립 검토를 한 차례 거쳤다. 지적 사항과 처리는 다음과 같다.

| 심각도 | 지적 | 처리 |
| --- | --- | --- |
| 높음 | 기존 코드가 오류를 `SystemExit`로 알려서 워커 안에서 부르면 워커나 프로세스가 죽는다 | 반영. 1단계에 예외 체계 교체를 넣음 |
| 높음 | 인증이 있는 SOCKS5 프록시는 Chrome이 지원하지 않는다. 계획의 예시가 틀렸다 | 반영. pydoll 소스에서 직접 확인하고 3.1을 고침 |
| 높음 | 파일 잠금은 한 프로세스의 워커끼리 소유자를 구분하지 못하고, 20분 뒤 잠금을 가져간다 | 반영. 프로세스 내 잠금으로 교체 (3.2, 1단계) |
| 높음 | 큐 유실, 중복 처리, 재시작 복구가 빠져 있다 | 큐 유실과 재시작 복구는 반영 (4.4). 두 워커의 중복 처리는 `jobs` 표의 갱신 한 번으로 막음 (3.3). 호출자 재전송에 대한 중복 방지 키는 단순화를 위해 첫 버전에서 뺌 (4.2) |
| 중간 | "확인된 사실" 표에 시험 범위를 넘은 서술이 있다 | 반영. 시험한 것과 추정을 나눠 다시 적음 (2장) |
| 중간 | `print` 출력은 동시 실행 시 인스턴스를 구분할 수 없고, 캐시 정리를 건너뛰어도 드러나지 않는다 | 반영. 로그 교체와 수치 기록 (3.2, 4단계) |
| 중간 | 모든 인스턴스가 같은 브라우저 신원을 쓴다 | 결정됨: Mac 에서는 macOS 와 Windows 신원을 절반씩 쓴다 (3.4, Q4) |
| 중간 | 여러 Chrome을 동시에 띄우면 디버깅 포트가 겹칠 수 있다 | 시험함. 8개 동시 기동 3회에서 충돌 없음. 겹치면 pydoll이 오류를 내므로 재시도와 선택적 포트 고정으로 대응 (3.2) |
| 중간 | 원본 반환의 크기, 민감 정보, 재전송 문제 | 반영. 기본값 꺼짐, 크기 상한, 내용 확인, 약관 검토 범위 추가 (4.3) |
| 중간 | 완료 기준이 검증하기 어렵다 | 반영. 횟수와 재현 방법을 넣음 (6장) |
| 낮음 | 잔여 Chrome 정리 대상 판단, 설정 파일 권한, 프록시 주소 노출, 운영 중 장애 대응, 입력 검증 | 반영 (3.1, 3.2, 4.2, 4.5) |

감사의 총평은 "큰 구조는 타당하나 1단계 범위를 넓히고 위 사항을 반영한 뒤 진행"이었다.
