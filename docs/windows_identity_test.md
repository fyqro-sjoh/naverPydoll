# Linux 컨테이너에서 Windows 신원으로 접속하는 시험 — 실행 계획

## 1. 질문

Linux(Docker)에서 실행하되 브라우저 신원(UA, Client Hints, 스크립트 값)만 Windows 로 바꾸면
네이버 가격비교 검색 페이지의 즉시 차단(HTTP 418)을 피할 수 있는가.

## 2. 지금까지 확인된 것 (비교 기준)

- Docker(Linux arm64, Chromium) + Linux 신원: 네이버 메인을 거쳐도 검색 페이지가 바로 418.
- Mac Chrome + Linux 신원(헤더의 OS 표기만 변경): 같은 IP 에서 바로 418.
- Mac Chrome + macOS 신원: 새 프로필은 405(보안 확인), 사람이 한 번 풀면 이후 200.

이 기준들은 어제 이전에 얻은 결과다. 오늘 다시 확인한 값이 아니다.

## 3. 코드 변경

- `fingerprints.py`: 환경 변수 `FINGERPRINT_OS`(`darwin` / `win32` / `linux`)로 프로필의 OS 를 지정한다.
  지정하지 않으면 지금처럼 실행 중인 OS 를 따른다. `build_full_profile()` 과 `window_size()` 가 이 값을 쓴다.
- `tests/identity_check.py`: 외부 접속 없이, 컨테이너 안의 로컬 서버로 브라우저가 실제로 내보내는
  헤더와 스크립트 값을 출력한다.
- 그 밖의 코드(접속 흐름, Slack 전달, 추출)는 바꾸지 않는다.

## 4. 실행 단계

모든 단계는 Docker 컨테이너(헤드리스), 직접 연결(프록시 없음)에서 한다.
Mac 의 통과된 프로필(`chrome-profile`)은 컨테이너에 연결하지 않는다.
판정 근거는 검색 페이지 문서의 `Status` 출력이다 (네이버 메인 요청의 상태는 기록되지 않는다).

| 단계 | 내용 | 통과 조건 | 실패 시 |
| --- | --- | --- | --- |
| 0 | 이미지 재빌드 후 `identity_check.py` 실행. 네이버 요청 없음 | 스크립트가 `RESULT: PASS` (헤더·스크립트 값이 Windows, `HeadlessChrome`·Linux 표기 없음, `webdriver` false) | 코드 수정 후 재확인. 다음 단계로 가지 않음 |
| 1 | (대조) 새 프로필 `profile-linux` + Linux 신원으로 검색 1회 | 418 재현 | 418 이 아니면 전제가 바뀐 것이므로 **중단하고 보고** |
| 2 | 120초 이상 쉰 뒤, 새 프로필 `profile-win` + Windows 신원, `--relay slack` 으로 검색 1회 | 418 이 아님 (405 또는 200) | 418 이면 **즉시 중단**, 재시도 없음 |
| 3 | 2단계에서 405 가 나오면 Slack 으로 전달된 보안 확인을 사람이 푼다 (같은 실행 안에서 이어짐) | 200 과 상품 40개 저장 | 대기 시간 초과·오답이면 그대로 기록하고 중단 |
| 4 | 3단계 통과 시, 90초 이상 쉰 뒤 같은 프로필로 `--pages 2` | 보안 확인 없이 200, 누적 80개 (전체가 80개 이상일 때) | 기록 후 중단 |
| 5 | 4단계 통과 시, 90초 이상 쉰 뒤 같은 프로필로 `--max-price 2500000` | 필터 API 200 | 기록 후 중단 |

대조를 맨 앞에 둔 이유: 2단계가 418 이든 아니든, 같은 날 같은 IP 의 Linux 신원 결과와 비교할 수 있어야 한다.
대조의 418 이 뒤 단계에 영향을 줄 가능성은 남는다 (이전 시험에서는 418 뒤에도 Mac 새 프로필이 405 였다).

실행 명령:

```
# 0단계
docker run --rm --init --name naver-id-check -e FINGERPRINT_OS=win32 \
  -v "$PWD/tests:/app/tests:ro" --entrypoint python naver-pydoll tests/identity_check.py

# 1단계 (대조)
docker run --rm --init --name naver-linux-test -e FINGERPRINT_OS=linux \
  -v "$PWD/docker-data:/data" naver-pydoll "LG 그램 16인치 5060" --wait-human 0 \
  --user-data-dir /data/profile-linux -o /data/products-linux.json

# 2~3단계
docker run --rm --init --name naver-win-test --env-file .env -e FINGERPRINT_OS=win32 \
  -v "$PWD/docker-data:/data" naver-pydoll "LG 그램 16인치 5060" --relay slack --wait-human 600 \
  --user-data-dir /data/profile-win -o /data/products-win.json

# 4단계: 위 명령에 --pages 2 추가 / 5단계: --max-price 2500000 추가
```

## 5. 지켜야 할 것

- 보안 확인은 자동으로 풀지 않는다. 답은 사람이 Slack 에 적는다.
- Windows 신원에서 418 이 한 번 나오면 그 단계에서 끝낸다. 같은 조건의 재시도는 하지 않는다.
- 실행 사이에 90초 이상 쉰다. 실행은 최대 5회이고, 실행 한 번은 문서 2건(메인, 검색)과 그에 딸린
  요청을 보낸다. 보안 확인 제출(오답 시 최대 3회)과 페이지·필터 API 호출 각 1건이 더해진다.
- 토큰은 `--env-file` 로만 넘기고 출력하거나 기록하지 않는다.
- 컨테이너는 `--rm --init --name` 으로 실행하고, 그 이름의 컨테이너만 정리한다.
  실행 전 `docker-data/relay` 폴더가 있는지, 비정상 종료 뒤 잠금 파일이 남았는지 확인한다.
- 시험 뒤 Mac 프로필 재확인은 이 시험에 포함하지 않는다 (같은 IP 라 영향이 섞인다).

## 6. 결과 해석의 한계 (미리 적어 둠)

- 이 Mac 의 Docker 는 arm64 Chromium 이다. x86 서버의 정식 Google Chrome 에서 같은 결과가 나온다는 보장은 없다.
- 직접 연결(가정용 회선)에서의 결과다. 서버 IP 나 프록시 IP 에서는 다를 수 있다.
- 각 단계를 한 번씩만 실행한다. 통과해도 "한 번 통과했다"는 뜻이고, 지속성은 알 수 없다.
- Windows 신원과 실제 렌더링(폰트, WebGL)의 불일치는 그대로 남는다. 0단계 출력에 그 불일치를 함께 기록한다.
- 0단계는 최상위 문서의 헤더와 페이지 스크립트 값만 본다. 워커·iframe 에서 나가는 값은 확인하지 않는다.
- 405 가 나오면 "Mac 새 프로필과 같은 취급"이라는 뜻이다. 사람이 한 번 풀어야 하는 것은 같다.
- 418 이 나오면 "한 번 418"까지만 말할 수 있다. 신원 외의 불일치(arm64, Chromium, 렌더링) 중 무엇 때문인지는 가릴 수 없다.
- 4~5단계의 통과는 신원보다 통과된 쿠키의 효과일 수 있다.

## 7. 결과 (2026-11-27)

### 한 줄 결론

Linux 컨테이너에서 Windows 신원으로 바꾸면 418 은 나오지 않았으나, 검색 페이지가 네이버 로그인 페이지로
넘겨져(307) 상품 목록은 받지 못했다. 보안 확인(405)도 나오지 않았다.
307 이 완화된 형태의 제한인지, 로그인을 요구하는 별도 정책인지는 알 수 없다.

### 실행 기록

| 실행 | 시각 | 신원 | 프로필 | 검색 페이지 응답 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 0단계 | — | Windows | 없음 | (네이버 요청 없음) | `RESULT: PASS` |
| A (1단계 대조) | 09:12:15 | Linux | 새 `profile-linux` | **418** | 코드 판정: 화면에 입력란·버튼·iframe 없음 |
| B (2단계) | 09:14:39 | Windows | 새 `profile-win` | **307** | 이동한 주소가 기록되지 않아 판정 불가 |
| C | 09:15:33 | Windows | `profile-win` | (요청 없음) | 브라우저 기동 실패. 아래 "Docker 운영 문제" |
| D (2단계 재실행) | 09:15:53 | Windows | `profile-win` (B 의 쿠키 있음) | **307 → 로그인 페이지(200)** | 제목 "NAVER 로그인" |

- 0단계에서 확인한 값: 헤더 UA `Windows NT 10.0; Win64; x64 … Chrome/156.0.0.0`, `sec-ch-ua-platform: "Windows"`,
  `navigator.platform` `Win32`, `webdriver` false, `HeadlessChrome`·Linux 표기 없음.
- 0단계에서 드러난 불일치: Windows 폰트 `Malgun Gothic` 이 "있다"고 답하지만 실제 글자 폭은 대체 폰트와 같다
  (`malgunGothicRendersDifferently: False`). WebGL 렌더러는 Direct3D 문자열로 답한다.
- D 의 이동 주소: `https://nid.naver.com/nidlogin.login?url=<원래 검색 주소>`.
- D 의 로그에 찍힌 `Status : 200` 은 검색 페이지가 아니라 넘겨진 로그인 페이지의 상태다.
  계획의 통과 조건에 적은 200(검색 페이지가 열림)과 같은 뜻이 아니다.
- 0단계 출력 원문은 실행 로그 파일에 모으지 않았다. 위 값은 실행 당시 화면 출력에서 옮겨 적은 것이다.
- 3~5단계(보안 확인 풀기, 페이지 넘김, 가격 필터)는 실행하지 않았다. 2단계에서 405 나 200 이 나오지 않아 조건이 성립하지 않았다.

### 계획과 달라진 점

- **계획에 없던 판단**: 계획은 2단계의 실패를 418 로만 정의했고 307 은 다루지 않았다. 어디로 넘겨졌는지
  알 수 없어, 실행 중에 판단해 2단계를 한 번 더 실행했다(D).
- **코드 수정과 이미지 재빌드**: D 전에 `stealth_visit.py` 의 `document_status()` 가 3xx 를 따라가 경로를
  출력하도록, `naver_products.py` 가 추출 실패 시 현재 주소와 제목을 출력하도록 고치고 이미지를 다시 빌드했다.
  A·B 는 수정 전 코드, D 는 수정 후 코드로 실행됐다. 브라우저와 신원 설정은 같다.
- **간격 미달**: B 종료에서 D 시작까지 67초로, 계획의 90초에 못 미쳤다. C 는 B 종료 47초 뒤의 시도였다
  (브라우저가 뜨지 않아 요청은 나가지 않았다).
- **쿠키가 있는 프로필**: D 는 새 프로필이 아니라 B 가 남긴 프로필에서 실행됐다.
- **잠금 파일 삭제와 호스트명 고정**: C 실패 뒤 `profile-win` 과 `profile-linux` 의 `Singleton*` 파일을 손으로
  지웠고, D 에 `--hostname naver-win` 을 추가했다.
- **신원 외에 달랐던 실행 조건**: A 는 Slack 전달 없이 `--wait-human 0`, B·D 는 `--relay slack --wait-human 600`.
  어느 실행도 보안 확인 화면에 이르지 않아 이 옵션이 동작한 구간은 없다.

### 해석

확인된 것:

- 같은 날, 같은 IP, 같은 브라우저 구성에서 신원(과 그에 따른 프로필 값)을 의도적으로 바꾼 두 조건의 응답이 달랐다:
  Linux 는 418, Windows 는 307. 실행 순서는 Linux 가 먼저였고(136초 간격), 순서를 바꾼 반복은 없다.
- Windows 신원에서 307 이 두 번 나왔다. 다만 두 번째(D)는 첫 번째(B)의 쿠키가 있는 상태였고, 첫 번째의
  이동 대상은 기록되지 않았다. 독립된 두 번의 재현이 아니다.
- D 에서 이동 경로 기록과 브라우저의 현재 주소·제목이 서로 같은 결과(로그인 페이지)를 보였다.

확인되지 않은 것:

- 418 이 사라진 것이 신원 때문인지. 실행 순서, 시점, 조건별 1~2회라는 횟수로는 단정할 수 없다.
- 로그인 페이지로 넘기는 이유. 후보는 신원과 실제 환경의 불일치(폰트, WebGL, arm64, Chromium, Linux Chromium 그대로인
  TLS·HTTP/2 지문), Windows 신원의 새 프로필에 대한 일반 정책, 오늘의 IP 상태, 직전 418 의 영향이다.
  Mac 에서 Windows 신원으로, 또는 Mac 신원의 새 프로필로 같은 날 접속해 본 적이 없어 가릴 수 없다.
- 로그인하면 상품 목록이 열리는지. 시험하지 않았다.
- 네이버 메인(사전 방문) 요청의 응답 상태. 기록 구간 밖이다.
- x86 서버, 정식 Google Chrome, 서버·프록시 IP 에서의 결과.

판정 코드의 한계: `document_status()` 는 주소 문자열이 정확히 같을 때만 이동을 따라가고, 스크립트나 meta 태그에
의한 이동은 따라가지 못한다. 따라가지 못하면 3xx 를 그대로 돌려준다 (정상으로 잘못 보고하지는 않는다).

### Docker 운영 문제

B 뒤와 D 뒤에 `profile-win` 폴더에 `SingletonLock`(→ `<컨테이너 호스트명>-<PID>`) 등 잠금 파일 3개가 남았다
(어제 만든 `profile` 에도 남아 있다). A 뒤 `profile-linux` 의 상태는 확인하기 전에 지워 기록이 없다.
Chrome 종료 뒤 잠금이 남는 현상 자체는 이미 알던 것이다. 새로 확인한 것은, 컨테이너마다 호스트명이 달라
Chromium 이 "다른 컴퓨터에서 사용 중"으로 보고 기동을 거부한다는 점이다(종료 코드 21, C 의 실패 원인).
이번에는 잠금 파일을 지우고 호스트명을 고정해 넘어갔다. 컨테이너에서 프로필을 재사용하려면
호스트명 고정이나 시작 시 잠금 정리가 필요하다.

## 8. 추가 시험: Mac 에서 Windows 신원 (2026-11-27)

Docker 에서 본 로그인 페이지 이동이 Windows 신원 자체 때문인지 가리려고, Mac 의 정식 Chrome(158, 헤드리스)에서
같은 Windows 프로필로 접속했다. 직접 연결, 새 프로필.

| 실행 | 시각 | 신원 | 프로필 | 검색 페이지 응답 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 사전 확인 | — | Windows | 없음 | (네이버 요청 없음) | `RESULT: PASS` |
| 대조 | 09:30:15 | macOS | 새 `chrome-profile-mactest-mac` | **405** | 보안 확인 요구. 풀지 않고 종료 |
| 본 시험 | 09:32:36 | Windows | 새 `chrome-profile-mactest-win` | **405 → 통과** | Slack 으로 사람이 답함. 전체 458개 중 40개 저장 |
| 재접속 | 09:35:04 | Windows | 같은 프로필 | **200** | 보안 확인 없이 열림. 40개 저장 |

확인된 것:

- Mac 에서는 Windows 신원도 macOS 신원과 같은 취급(새 프로필 405)을 받았고, 사람이 한 번 풀자 상품 목록이 열렸다.
  로그인 페이지로 넘겨지지 않았다.
- 같은 날 같은 IP 에서 대조가 405 였으므로, Docker 의 418 과 307 은 오늘의 IP 상태 때문이 아니다.
- 따라서 Docker 에서의 로그인 페이지 이동은 Windows 신원 자체가 아니라 Linux 컨테이너 쪽 요인과 함께 나타난다.
  그 요인이 무엇인지(Chromium 빌드, arm64, 소프트웨어 렌더링, 폰트 등)는 가리지 못했다.

한계:

- 이 시험의 Windows 신원도 실제 환경(Mac)과 어긋나 있다(폰트 폭, GPU). 그 상태로 통과했다는 것이지,
  Windows 실기기에서의 결과를 확인한 것은 아니다.
- 조건별 1회다. 가격 필터, 정렬, 페이지 넘김은 Windows 신원으로 시험하지 않았다.
